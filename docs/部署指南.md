# 部署指南：Google Cloud e2-micro 服务器

部署有两种方式。**推荐使用第 9 节的自动部署**：完成一次性设置后，每次把代码推送到 `main` 分支，GitHub Actions 会自动运行测试、构建发布包、上传到服务器并完成安装，不需要再手动操作服务器。第 3 节的手动部署适合第一次试用，或者在 GitHub Actions 暂时不可用时使用。两种方式使用的是同一套安装和发布脚本，可以随时切换。

本指南说明如何把工程资源申请系统部署到已经运行 PMate 的 Google Cloud 服务器上。整个过程不会修改 PMate 及其 Caddy 配置，新系统通过一个独立的 Caddy 站点文件接入。

## 1. 部署架构

| 组件 | 位置 | 说明 |
| --- | --- | --- |
| 前端静态文件 | `/opt/erf/current/frontend` | 由现有的 Caddy 直接托管，并自动申请 HTTPS 证书。 |
| 后端服务 | systemd 服务 `erf`，监听 `127.0.0.1:8100` | 只接受本机请求，外部无法直接访问。内存上限 320 MB，不会影响 PMate。 |
| 后台任务 | 与后端在同一个进程中运行 | 负责发送邮件、超时提醒、自动关闭和清理过期会话。 |
| 数据库 | `/var/lib/erf/erf.db`（SQLite） | 只有 `erf` 用户可以读写。 |
| 备份 | `/var/lib/erf/backups` | systemd 定时器每天新加坡时间 02:30 备份一次，保留最近 30 份。每次发布新版本前也会自动备份。 |
| 配置 | `/etc/erf/erf.env` | 只有 root 和 `erf` 组可以读取。 |
| Caddy 站点 | `/etc/caddy/sites/erf.caddy` | 由主 Caddyfile 末尾的 `import /etc/caddy/sites/*.caddy` 自动加载。 |
| 程序版本 | `/opt/erf/releases/<时间戳>` | `/opt/erf/current` 指向当前版本，保留最近 5 个版本以便回滚。 |

## 2. 准备工作

### 2.1 域名

系统使用 DuckDNS 子域名 `psbu.duckdns.org`，它需要指向服务器的外部 IP `136.86.169.145`。可以在 DuckDNS 页面上确认 IP 是否正确，也可以在任意电脑上运行 `nslookup psbu.duckdns.org` 检查。

### 2.2 准备发布包

发布包是一个 `.tar.gz` 文件，里面包含后端代码、已经构建好的前端文件和部署脚本。服务器上不需要安装 Node.js。

- 测试阶段可以直接使用我发给你的 `erf-<版本号>.tar.gz`，它是演示模式的构建，登录页面会列出演示账号。
- 以后可以在任何装有 Node.js 的电脑上，在仓库根目录运行 `deploy/scripts/build-release.sh --demo`（演示版）或 `deploy/scripts/build-release.sh`（正式版）生成新的发布包。代码推送到 GitHub 后，GitHub Actions 也会在每次推送到 `main` 分支时自动生成发布包。

## 3. 首次部署

以下操作都在 Google Cloud 控制台的浏览器 SSH 窗口中完成。

**第一步：上传发布包。** 点击 SSH 窗口右上角的“上传文件”，选择发布包。文件会上传到你的用户主目录。

**第二步：解压发布包，准备运行部署脚本。** 把下面命令中的文件名换成实际的文件名：

```bash
mkdir -p ~/erf-release && tar -xzf ~/erf-*.tar.gz -C ~/erf-release
```

**第三步：初始化服务器。** 这一步会创建 `erf` 系统用户和所需目录，安装 uv，安装 systemd 服务和 Caddy 站点文件，然后校验并重新加载 Caddy。这个脚本可以重复运行，不会覆盖已有的配置文件。

```bash
sudo bash ~/erf-release/deploy/scripts/install.sh --domain psbu.duckdns.org
```

**第四步：检查配置文件。** 测试阶段可以保持默认值。邮件默认只写入日志，不会真正发送。

```bash
sudo cat /etc/erf/erf.env
```

**第五步：安装发布包并导入演示数据。** 首次运行时，uv 会下载 Python 和依赖，大约需要一两分钟。

```bash
sudo bash ~/erf-release/deploy/scripts/release.sh ~/erf-*.tar.gz --seed-demo
```

看到 `Release … is healthy.` 就表示部署成功。现在可以打开 `https://psbu.duckdns.org`，用登录页面列出的演示账号登录，所有演示账号的密码都是 `Demo@2026!`。

## 4. 发布新版本

上传新的发布包后，运行下面的命令即可。这次不需要加 `--seed-demo`，已有数据会保留。

```bash
sudo bash ~/erf-release/deploy/scripts/release.sh ~/erf-<新版本号>.tar.gz
```

脚本会依次完成以下步骤：解压到新的版本目录、创建 Python 环境、备份数据库、执行数据库迁移、切换 `/opt/erf/current` 链接、重启服务并检查健康状态。如果新版本在 30 秒内没有通过健康检查，脚本会自动切回上一个版本。

## 5. 日常运维

查看服务状态和最近的日志：

```bash
systemctl status erf
```

```bash
journalctl -u erf -n 100 --no-pager
```

查看内存占用：

```bash
systemctl show erf -p MemoryCurrent
```

手动备份数据库：

```bash
sudo systemctl start erf-backup
```

查看备份文件：

```bash
sudo ls -lh /var/lib/erf/backups
```

创建管理员账号，或者重置某个管理员的密码。命令会输出一个临时密码，首次登录时必须修改：

```bash
cd /opt/erf/current/backend && sudo -u erf bash -c 'set -a; . /etc/erf/erf.env; set +a; .venv/bin/erf create-admin --email you@company.com --name "Your Name"'
```

## 6. 从备份恢复数据库

```bash
sudo systemctl stop erf
```

```bash
sudo -u erf cp /var/lib/erf/backups/erf-<时间戳>.db /var/lib/erf/erf.db
```

```bash
sudo systemctl start erf
```

## 7. 开启真实的邮件发送（Gmail）

系统通过 Gmail 的 SMTP 服务（`smtp.gmail.com`，587 端口）发信。Google Cloud 只封锁出站 25 端口，587 端口可以正常使用。邮件设置由自动部署写入服务器，密码只保存在 GitHub Secrets 中，不会出现在代码仓库里。

**第一步：生成 Gmail 应用专用密码。** Gmail 不允许用登录密码直接发信，必须使用应用专用密码，而创建它的前提是账号已经开启两步验证。

1. 登录 `leytoray@gmail.com`，打开 Google 账号的 **安全性** 页面，确认“两步验证”已开启。
2. 在同一页面搜索“应用专用密码”（App passwords），新建一个，名称可以填 `ERF`。
3. Google 会显示一个 16 位密码。请立即复制，关闭窗口后无法再次查看。

**第二步：在 GitHub 中添加设置。** 打开仓库的 **Settings → Secrets and variables → Actions**：

| 位置 | 名称 | 值 |
| --- | --- | --- |
| Secrets | `ERF_SMTP_PASSWORD` | 第一步得到的 16 位应用专用密码，中间的空格可以保留，部署时会自动去掉 |
| Variables | `ERF_SMTP_USERNAME` | `leytoray@gmail.com` |

**第三步：重新运行部署。** 在 **Actions → CI → Run workflow** 中选择 `main` 分支运行。部署会把邮件设置写入服务器的 `/etc/erf/erf.env`，然后重启服务。

**演示模式下的邮件。** 当变量 `ERF_DEMO` 为 `true` 时，所有通知都会发送到 `leytoray@gmail.com`，主题中会注明原本的收件人，正文顶部也有说明。这是因为演示账号的邮箱都是不存在的 `@example.com` 地址，直接发送只会产生大量退信。把 `ERF_DEMO` 改为 `false` 并重新部署后，邮件会发给真实的收件人。

**检查发送情况。** 管理员可以在系统的 “Settings → Email delivery” 页面查看每封邮件的状态。如果显示失败，最常见的原因是应用专用密码填写错误。Gmail 个人账号每天大约可以发送 500 封邮件，对这个系统来说足够。

## 8. 从演示环境转为正式环境

1. 用正式版发布包（`build-release.sh` 不带 `--demo`）重新发布，登录页面将不再显示演示账号。
2. 用 `create-admin` 创建自己的管理员账号，然后在 “Settings → Users” 中停用所有 `@example.com` 演示账号，并创建真实用户。
3. 在 “Settings” 中确认支持类型、团队审批人、公共假期和工作流参数。
4. 如果要从空数据库开始，请先备份并停止服务，再删除 `/var/lib/erf/erf.db`，然后重新运行 `release.sh`（不带 `--seed-demo`）。

## 9. 自动部署（GitHub Actions）

### 9.1 工作方式

`.github/workflows/ci.yml` 中的 `deploy` 任务在每次推送到 `main` 分支、且后端和前端检查全部通过后运行：

1. 构建发布包，并作为构建产物保存 30 天，需要时可以手动下载。
2. 通过 SSH 把发布包上传到服务器的 `/tmp`。
3. 在服务器上依次运行 `install.sh`（可重复运行，用于同步 systemd 和 Caddy 配置）和 `release.sh`（备份、迁移、切换版本、健康检查，失败时自动回滚）。
4. 访问 `https://psbu.duckdns.org/api/health`，确认网站可以从公网访问。

在设置好变量 `DEPLOY_ENABLED` 之前，这个任务只构建发布包，不会连接服务器。

### 9.2 一次性设置

**第一步：生成部署专用的 SSH 密钥。** 在服务器的浏览器 SSH 窗口中运行下面的命令。它会在当前目录生成一对密钥，并且不设密码短语，因为 GitHub Actions 需要无人值守地使用它：

```bash
ssh-keygen -t ed25519 -N "" -C github-deploy -f ~/github-deploy
```

**第二步：把公钥添加到虚拟机。** 显示公钥内容：

```bash
cat ~/github-deploy.pub
```

在 Google Cloud 控制台打开 **Compute Engine → VM 实例 → 你的实例 → 修改**，在 **SSH 密钥** 部分点击“添加项”，粘贴这一整行内容后保存。Google Cloud 会自动在服务器上创建 `github-deploy` 用户，并授予它免密码的 sudo 权限。如果你的项目启用了 OS Login，这种方式不会生效，请告诉我，我会改用其他方法。

**第三步：获取服务器的主机指纹。** GitHub Actions 会用它确认连接的确实是你的服务器，防止中间人攻击：

```bash
echo "136.86.169.145 $(cut -d' ' -f1,2 /etc/ssh/ssh_host_ed25519_key.pub)"
```

**第四步：在 GitHub 中添加 Secrets 和 Variables。** 打开仓库的 **Settings → Secrets and variables → Actions**。

在 **Secrets** 页签中添加以下四项：

| 名称 | 值 |
| --- | --- |
| `DEPLOY_HOST` | `136.86.169.145` |
| `DEPLOY_USER` | `github-deploy` |
| `DEPLOY_SSH_KEY` | 私钥文件 `~/github-deploy` 的完整内容（运行 `cat ~/github-deploy` 显示），包括首尾的 `-----BEGIN…` 和 `-----END…` 两行 |
| `DEPLOY_KNOWN_HOSTS` | 第三步输出的那一行 |

在 **Variables** 页签中添加以下几项（邮件相关的设置见第 7 节）：

| 名称 | 值 | 说明 |
| --- | --- | --- |
| `DEPLOY_ENABLED` | `true` | 改为 `false` 可以暂停自动部署 |
| `ERF_DOMAIN` | `psbu.duckdns.org` | |
| `ERF_DEMO` | `true` | 演示模式：登录页显示演示账号，并在首次部署时导入模拟数据。正式使用前改为 `false` |

**第五步：删除服务器上的私钥文件。** 私钥只需要保存在 GitHub Secrets 中：

```bash
rm ~/github-deploy ~/github-deploy.pub
```

**第六步：确认防火墙允许 SSH。** GitHub Actions 从公网连接服务器的 22 端口。Google Cloud 默认网络自带的 `default-allow-ssh` 规则允许所有来源访问 22 端口。如果你修改过这条规则，只允许浏览器 SSH 使用的 IAP 地址段，自动部署将无法连接。可以在 **VPC 网络 → 防火墙** 中确认。

### 9.3 触发部署

- 把代码合并或推送到 `main` 分支，部署会自动开始。
- 也可以在 GitHub 仓库的 **Actions → CI → Run workflow** 中手动运行，选择 `main` 分支即可。

每次运行的详细输出都可以在 **Actions** 页面查看。如果部署失败，把失败步骤的日志发给我。
