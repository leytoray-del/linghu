Permissions: who can see and do what

For review13 Nov 2026Applies to every module and the menus

This page shows how access works in OpsHub today, where it falls short, and a finer-grained design that stays easy to manage. The interactive preview shows which menu items and which + New options each role gets.

Today

How access works now

Access is already decided in three ways. The foundation is sound, but administrators cannot change what a role allows, and the two modules check access differently.

1. Roles works

Eight roles: Requester, Engineer, Team leader, Director, Operations manager, Inventory clerk, Viewer and Administrator. A person can hold several. The administrator assigns them on the Users page or by Excel import.

2. Permissions partly

Inventory pages check permissions such as inventory.view and inventory.register. Which role gets which permission is written in the code, so changing it needs a release. The resource request pages still check role names directly.

3. Assignments works

Some rights come from a relationship, not a role: the approvers of a team review that team's requests, and the PM named on a project will approve its withdrawals. This is correct and stays.

What is missing

  • An administrator cannot adjust a role, for example let clerks export but not edit, or create a read-only "Store keeper" role.
  • There is no data scope for inventory: everyone who can see inventory sees every project.
  • Menus are wired to roles in two different ways, so a new module or role needs code changes in several places.
Proposal

One model for every module

The standard role-based access model (RBAC), with a data scope on each permission and assignments for approvals. Administrators work with roles; the system works with permissions.

UserHolds one or more roles
RoleA named set of permissions, edited by the administrator
Permission + scopeinventory.item.view for my projects or all
AssignmentTeam approver, project PM: who decides a specific request

The rule: an action is allowed when one of the person's roles grants the permission, the record is inside that permission's scope, and, for approvals, the person is the assigned approver of that record.

Permissions are named by module, object and action

resources.request.approve, inventory.device.register. Each module declares its own permissions, with a description and the roles that get them by default. A new module's permissions appear on the roles screen automatically.

Scopes limit which records

Own (what I raised or hold), My teams, My projects (projects I manage or am assigned to), All. With several roles, the widest scope applies.

Menus follow permissions

Every menu item, every + New option and every button names the permission it needs. There is no separate menu setting to keep in step, so a person never sees a page they cannot use.

Safeguards

  • The Administrator role always has every permission and cannot be edited.
  • At least one active administrator must remain; nobody can remove their own administrator role.
  • System roles can be adjusted but not deleted; custom roles can be added and removed.

Traceable

  • Every change to a role or to a person's roles is recorded: who, when, before and after.
  • A change takes effect on the person's next page load, without signing out.

No surprise on the switch-over

  • The current roles are created with exactly the access they have today, so nobody gains or loses anything when this is released.
  • Existing data and accounts stay as they are.
Delivery

How it would be built

Data

Two new tables, roles and role_permissions (with the scope), added by an incremental migration. The existing role assignments stay and point at the new roles.

Server

One check, require(permission) plus a scope filter on lists, replaces the role checks in the resource module. Each module declares its permissions in its module definition.

Screens

The Roles and permissions screen, the menu and + New built from permissions, and "Preview as this role". The automated tests for today's behaviour must all keep passing.

Decisions needed

No.QuestionRecommendation
P1Should administrators be able to add their own roles, such as "Store keeper"?Yes. The system roles cover most people; custom roles cover exceptions.
P2Who may see inventory: everyone, or only people on the project?Everyone sees all projects by default (scope All); limit a role to "My projects" if needed.
P3May engineers register devices, or only inventory clerks?Clerks only by default. Grant "Register devices" to Engineer later if needed.
P4Should writing off an item need a separate permission?Yes. It is final, so it is kept for Operations manager and Administrator.
