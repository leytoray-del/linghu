Engineering Resource Request System · design proposal

Inventory module for FR readers

Draft for review Date 12 Nov 2026 Scope Record, track and withdraw FR readers Built Not yet; this is the design

Suppliers deliver FR readers to NEC, and support engineers deploy them to project sites. Today there is no shared record of where each reader is, which project it belongs to, or when its warranty ends. This module adds that record to ERS. It also adds a controlled way for engineers to withdraw readers from stock, with approval by the project manager and the operations manager.

Workflow

How readers move through the system

There are two everyday workflows: registering a delivery, and withdrawing readers for a project. Both change the state of each reader, shown in the lifecycle diagram at the end of this section.

Engineer Project manager Operations manager Inventory clerk System
  1. Engineer

    Create the request

    Choose the project, then add readers by scanning them or picking from the available stock. Give the purpose, the destination site and the date needed.

  2. Engineer

    Submit

    Waiting for PM

    The system checks that every reader is in stock, belongs to the project and is not in another open request. The project's PM gets an email with Approve and Reject buttons.

  3. Project manager

    First approval

    Waiting for OM

    The PM approves in the system or from the email. If the requester is the PM, this step is skipped and the reason is recorded.

  4. Operations manager

    Final approval

    Approved

    Any operations manager can approve. Nobody can approve their own request.

    If the PM or OM rejects: the request goes back to the engineer with the comment. The engineer can revise and resubmit it, or withdraw it. The readers stay available to others.
  5. System

    Reserve the readers

    Reserved

    The readers are held for this request so no one else can take them. The engineer and the clerks get a "ready for collection" email. If nobody collects them within 10 working days, the clerk is reminded.

  6. Clerk and engineer

    Handover

    Issued

    The engineer scans each reader at the store. A reader that is not in the request is refused, and the handover cannot finish while one is missing. The engineer becomes the holder of the readers.

  7. Engineer

    Deploy or return

    Deployed

    The engineer marks each reader as deployed, with the site and date, or returns unused readers to the store. The request closes when every reader is deployed or returned.

  1. Inventory clerk

    Start a delivery

    Enter once for the whole delivery: supplier, delivery order number, project, reader model, store location, warranty start and end dates.

  2. Inventory clerk

    Scan the readers

    Point the phone camera at each label. Each scan adds a reader with a beep and a counter. A duplicate within the delivery, or a serial number already in the system, is flagged straight away. A handheld scanner or typing also works.

  3. Inventory clerk

    Add optional details

    Tap any reader to add FR ID, deployment date, OS, firmware and APK versions, or mounting type. These can also be added later, or by Excel import.

  4. System

    Save the delivery

    In stock

    All readers are saved together. Each gets a "Received" entry in its history, linked to the delivery record.

Reader lifecycle

A reader's state changes only through actions such as Issue, Return or Report fault. Nobody edits the state directly, and each change is written to the reader's history.

Access

Roles and permissions

The module uses the existing ERS accounts. It adds two roles, Inventory clerk and Operations manager. The PM is not a role: each project names its PM, and withdrawals for that project go to that person.

RoleWhoWhat they can do
Inventory clerk newSupport engineers who receive deliveriesRegister deliveries, edit reader details, hand over approved readers, record returns, transfers and repairs, run stocktakes.
EngineerField and support engineersView stock, request readers, confirm handover, deploy, return and report faults.
Project managerThe PM named on each projectApprove or reject withdrawals for their own projects (first level).
Operations manager newOMApprove or reject withdrawals after the PM (second level). See all inventory and reports.
ViewerManagementRead-only access to inventory and reports.

Data

What is recorded

Each physical reader is one record, identified by its serial number. Lists such as models, projects and locations are chosen from maintained lists rather than typed, which keeps the reports accurate.

Reader

serial no. (unique) · model no. · project · location · warranty start · warranty end · status · holder
optional: FR ID · deployment date · OS version · firmware version · APK version · mounting type · remarks

Bold fields are mandatory, as in your requirement.

Delivery (goods receipt)

receipt no. (GRN-2026-0042) · supplier · delivery order no. · received on · received by · default project, model, location and warranty dates

Reader history

reader · action (received, reserved, issued, deployed, returned, repaired, disposed, edited) · from and to state · from and to location · from and to holder · request · who · when · reason

Only ever added to. It is the audit trail.

Withdrawal request

request no. (WDR-2026-0014) · engineer · project · purpose · destination · date needed · status · readers in the request · PM and OM approval steps with comments

Lists maintained by the administrator

reader models (with serial no. format) · projects with their PM · store and site locations · suppliers
Architecture

How it fits into ERS

Inventory is a separate module inside the same application, an approach known as a modular monolith. It has its own data, rules, pages and API, and it reuses the parts of ERS that already work. This suits a small team and the current server, and the module could still be separated later if needed.

Reused from ERS

  • Accounts, sign-in and roles
  • Two-level approval with email Approve and Reject buttons
  • Email queue, reminders and the working-day calendar
  • Excel import with a preview, and Excel export
  • Automatic deployment and daily database backup

New in the module

  • Reader, delivery, history and withdrawal tables, added by an incremental database update
  • Lifecycle and withdrawal rules, each defined as a table of allowed transitions
  • Camera scanning component for phones
  • Inventory pages and the /api/v1/inventory API

Industry practices followed

  • Serialised asset register (ISO/IEC 19770-1)
  • Goods receipt for each delivery
  • History log that cannot be edited
  • Separation of duties: no self-approval
  • Reservation on approval, confirmed handover
  • Regular stocktake by scanning
Delivery

Three phases

Each phase is released on its own, with an incremental database update and no data replaced.

1

Register and find

Lists, mobile delivery registration with scanning, reader list and details with history, Excel import of existing readers, Excel export.

2

Withdraw and issue

Withdrawal requests, PM and OM approval including from email, reservation, handover by scanning, deploy, return and report fault.

3

Monitor

Warranty reminders and report, stock reports, stocktake by scanning a whole store.
