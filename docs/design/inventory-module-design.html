System design · revised

PSBU OpsHub: one system for engineering operations

Draft for review Date 12 Nov 2026 Modules Resources (live today), Inventory (new: any equipment, kept by project) Address psbu.duckdns.org

The resource request system and the new inventory function serve the same people: project managers, engineers, team leaders, directors and operations managers. They should therefore be one system, with one sign-in, one menu and one inbox, organised into modules. This revision replaces the earlier design, which treated inventory as a separate area.

The system is built as a platform with a shared core and pluggable modules. Resource requests become the first module, inventory becomes the second, and further modules can be added later without changing the core or the existing modules.

System name

A name that covers every module

"Engineering Resource Requests" describes only the first module. The new name should cover engineering operations as a whole, so it stays accurate as modules are added. Each module keeps a plain descriptive name inside the system.

Adding a new category

  • Name it, for example "Camera", and choose whether warranty dates are required.
  • Add its fields: text, number, date, choice or yes/no.
  • Add its models, each with an optional serial number format for scanning.
  • It is ready to use at once, in every project.

Fields can be added or retired later. Retired fields keep their recorded values.

Architecture

A shared core with pluggable modules

The system stays one application on one server, in a style known as a modular monolith. Everything that more than one module needs lives in the platform core. Each module owns its own data, rules and pages, and talks to the core through defined interfaces, never directly to another module.

What every module provides

A module plugs into the core by declaring these items in one module definition. The core builds the menu, home page, inbox, search and reports from them.

  • Its menu section and its items in + New
  • Its permissions, such as inventory.withdrawal.create
  • Its document types and their approval routes
  • Home page cards and "needs your action" items
  • Search providers, for example by serial number
  • Tabs for the project page, Reports and Administration
  • Its own tables, migrations and email templates

Rules that keep it extensible

  • Modules use the core only through its interfaces, and never read another module's tables.
  • Cross-module links go through shared records, mainly projects and users.
  • Access is checked by permission, not by role name, so new roles need no code changes.
  • Each module's tables have its prefix (res_, inv_) and its own migrations in the single migration chain.
  • A module can be switched off in settings without affecting the others.

Access

Roles across modules

Roles are shared across the whole system, and one person can hold several. Each role is a named set of permissions, so the administrator can adjust what a role may do, and new modules add permissions without new code for access checks.

Workflow

Approval routes on one engine

Every module uses the same approval engine. A route is a list of steps, and each step names who decides. The engine handles the rest in the same way for every module: email with Approve and Reject buttons, reminders, Reject sending the request back for revision, no self-approval, and the full history.

Resource request

Resources
Requester→Team leader of the team→Director
  • The team leader also assigns engineers and their time.
  • Live today; moves onto the shared engine without changing how it works.

Item withdrawal

Inventory
Engineer→PM of the project→Operations manager
  • The PM step is skipped, with the reason recorded, when the engineer is the project's PM.
  • Approved items are reserved until handover.

Transfer between projects

Inventory
Clerk or PM→PM of the receiving project→Operations manager
  • For example, spare readers from one project reused on another.
  • The history records both projects and the reason.

Future document type

Any module
Requester→Step 1→Step 2 …
  • Each step's approver is chosen by a rule: a role, the project's PM, the team's leader, or a named person.
  • Configured in Administration, not in code.

Item withdrawal, step by step

Engineer Project manager Operations manager Inventory clerk System
  1. Engineer

    Create and submit

    Waiting for PM

    From the project's inventory page, or + New, choose Request items. Add specific items by scanning or from the project's stock, or ask for a model and a quantity. The system checks that each item is in stock, belongs to the project and is not in another open request.

  2. Project manager

    First approval

    Waiting for OM

    The request appears in the PM's Approvals inbox next to their other approvals, and they also get an email with Approve and Reject buttons.

  3. Operations manager

    Final approval

    Approved

    Any operations manager can approve. Nobody can approve their own request.

    If the PM or OM rejects: the request goes back to the engineer with the comment, who can revise and resubmit it or withdraw it. The items stay available.
  4. System

    Reserve the items

    Reserved

    Specific items are held for this request. The engineer and the clerks are told they are ready for collection, and the clerk is reminded if nobody collects them within 10 working days.

  5. Clerk and engineer

    Handover by scanning

    Issued

    The clerk picks items for any model-and-quantity lines, and the engineer scans every item. An item not in the request is refused, and the handover cannot finish while one is missing.

  6. Engineer

    Deploy or return

    Deployed

    Each item is marked as deployed at a site, or returned to the store. The request closes when all items are accounted for. The project's inventory page shows the result.

Data

Shared records connect the modules

Users, teams and projects belong to the core, so every module refers to the same project and the same person. This is what lets the project page show engineers and equipment together.

Core Shared records

  • Users and their roles
  • Teams and team leaders
  • Projects: WBS code, name, client and PM. Inventory is kept under projects, and resource requests link to them. Today a project is typed into each resource request; it becomes a list, with existing names matched during migration.
  • Locations: stores and sites
  • Approval tasks and history for every document type

Resources Module records

  • Resource requests, linked to a project
  • Engineer allocations with percentages
  • Changes after approval

Inventory Module records

  • Categories such as FR reader, camera, gateway, tablet, each with its own fields
  • Models, each in one category, and suppliers
  • Items: serial no., model, project, location, warranty dates, plus the category's own fields
  • Deliveries, each for one project
  • Withdrawals and transfers between projects
  • Item history, which is only ever added to
Delivery

Four phases

The platform work comes first, so that inventory is built on the shared core from the start. Every phase keeps the existing data and uses incremental database updates only.

0

Platform foundation

New name, combined menu, + New, one Approvals inbox, project list, permission-based roles, and the approval engine. Resource requests move onto the core with no change for users, protected by the existing automated tests.

1

Inventory: register and find

Categories with their fields (FR reader first), models, the project inventory page, deliveries with scanning on a phone, item history, Scan and search, Excel import and export per project.

2

Inventory: withdraw and issue

Withdrawals with PM and OM approval, reservation, handover by scanning, deploy, return and report fault, transfers between projects.

3

Monitor and extend

Warranty reminders, stocktake by scanning, reports by project and category, items counted by quantity if needed. Then the next module, using the same pattern.
